# Facility Booking: Recommendations from Buzz

This document compares the booking pipeline the `buzz` app uses for event ticketing against what `sports_complex` currently has for facility booking (Facility Booking, Booking Schedule, Booking Cancellation, Court, Sports Facility, Maintenance Schedule, Venue). Buzz solves a structurally similar problem — reserve a limited resource for a time-bound event, take payment, allow self-service changes — and its code is mature enough to lift patterns from directly rather than reinvent them.

The short version: `sports_complex`'s booking doctypes are solid on the data-modeling and staff-desk side (overlap checking, maintenance conflicts, credit notes), but the entire self-service layer that Buzz has — a customer or member booking and paying for a court without staff creating the record for them — doesn't exist yet. Everything below is organized around closing that gap, plus a couple of correctness issues worth fixing regardless.

## What sports_complex has today

Facility Booking is a submittable, desk-only doctype. A staff member (Sports Complex Staff/Manager, or System Manager) fills in customer, court, date, and start/end time; `validate()` checks the times are sane, computes duration and `total_amount` from the court's hourly rate, and runs two SQL overlap checks — one against other Facility Bookings on the same court and date, one against Maintenance Schedule — before allowing the record to save. On submit it creates a Sales Invoice against an Item named after the court's Facility Type. Booking Cancellation is a separate submittable doctype that flips the booking's status to Cancelled and can optionally generate a credit note via ERPNext's `make_sales_return`. Booking Schedule exists as a per-court, per-day-of-week template of open slots (start, end, duration, active flag), but nothing in the codebase actually reads it — no code generates a slot list from it or validates a booking's start/end time against it. There's no www/ page, no whitelisted API method, and no portal role anywhere in this pipeline; every one of these doctypes is only reachable from the Frappe desk.

## What Buzz does that sports_complex doesn't

**Self-service booking end-to-end.** Buzz's `process_booking` whitelisted method (`allow_guest=True`) takes a `BookingRequest`, validates the event is live and registration is still open, resolves the caller to either the logged-in user or a guest (email + OTP, or phone + OTP, depending on the event's `guest_verification_method`), builds the booking, and branches three ways depending on price and payment method: free bookings submit immediately, offline-payment bookings go to an "Approval Pending" staff-review state with an attached payment-proof file, and everything else gets a payment gateway link. Facility Booking has no equivalent entry point — there is no way for a customer to reach this flow without a staff member operating the desk form for them.

**Availability as a real check, not just overlap detection.** Event Ticket Type computes `remaining_tickets` as `max_tickets_available - tickets_sold` (with `-1` meaning unlimited) and exposes `are_tickets_available(n)`; the booking flow calls this before committing. Facility Booking only prevents a *specific* time range from double-booking after the fact — it has no equivalent of "how many courts of this type are free right now" or "list the open slots for court X on date Y," which is what a booking UI actually needs to render. Booking Schedule is exactly the input you'd need to compute that (it already models day-of-week slot templates) but nothing turns it into a queryable availability endpoint the way `remaining_tickets` does.

**Guest/self-service access without exposing sequential IDs.** Buzz signs booking names with `hmac.new(get_encryption_key().encode(), booking_name.encode(), hashlib.sha256)` to produce a per-booking access token (`get_booking_access_token` / `verify_booking_access_token`), so a guest whose session is still "Guest" can open their own confirmation page via a URL token instead of needing a login, while the token still makes booking IDs unguessable (no IDOR by walking sequential names). If member/guest self-service booking is added to Facility Booking, this is the pattern to copy rather than something bespoke — it's a genuinely non-obvious primitive (most people reach for a random UUID field, which adds a column and a lookup; this is a stateless HMAC that needs no storage).

**Configurable, time-windowed self-service policies.** Buzz Settings (a singleton, System-Manager-only) holds `allow_transfer_ticket_before_event_start_days`, `allow_add_ons_change_before_event_start_days`, and `allow_ticket_cancellation_request_before_event_start_days`, each defaulting to 7. A small `windows.is_window_open(event, WINDOW_TYPE)` helper compares "now" against the event start minus that many days and returns whether the action is still allowed. Booking Cancellation has no time-based policy at all right now — the only guard is `booking_status not in ('Cancelled', 'Completed')`, so a customer could in principle cancel (or, once self-service exists, request cancellation of) a booking five minutes before it starts. A `Sports Complex Setup` (or a new `Booking Settings`) singleton with something like `allow_cancellation_before_booking_hours` mirrors this exactly, just in hours instead of days since court bookings are same-day/next-day rather than months out.

**A request/approval step for cancellation, not direct staff-only cancel.** Buzz separates "customer asks to cancel" (Ticket Cancellation Request, a submittable doc with status In Review/Accepted/Rejected, holding either individual ticket rows or a cancel-full-booking flag) from "cancellation actually happens" (which only fires in `on_submit()` once status is Accepted, and calls `.cancel()` on the underlying ticket or booking doc). Booking Cancellation in sports_complex conflates these — creating and submitting the doctype *is* the cancellation, with no review step and no doctype-level restriction on who's allowed to submit it beyond staff roles. If members are ever going to request their own cancellations, you want the two-phase version: a request they can create, and a staff (or auto-) approval that's the only thing allowed to flip Facility Booking's status.

**A generic, gateway-agnostic payment-link abstraction.** `get_payment_link(reference_doctype, reference_docname, amount, currency, payment_gateway, ...)` in Buzz's `payments.py` works against *any* reference doctype — it's used for both Event Booking and Sponsorship Enquiry today, and records an `Event Payment` doc plus calls into Frappe's generic `payments` app controller (`get_payment_gateway_controller`) so adding a new gateway doesn't touch the booking code at all. `frappe_paystack` (which this project already has, complete with a Vue checkout page) is a *direct*, Paystack-specific integration — it isn't wired into Facility Booking's `create_sales_invoice()` at all right now. That's the actual gap worth closing: Facility Booking creates a Sales Invoice and stops, so there's no self-checkout path from "customer wants to book" through "customer pays online" — a staff member has to separately collect payment against the invoice. Given frappe_paystack already exists in this codebase, the natural fix isn't to copy Buzz's generic multi-gateway abstraction wholesale, but to add one whitelisted method that, given a Facility Booking name, creates (or reuses) the Sales Invoice and returns a `paystack-checkout` link the way frappe_paystack's other checkout flows already do.

**QR-coded, individually cancellable units.** Buzz issues one Event Ticket per attendee (with its own QR code via `generate_qr_code_file`, used for check-in scanning and emailed as a calendar invite attachment), and cancellation can target individual tickets rather than only the whole booking. Facility Booking is single-unit (one booking = one court = one time slot), so this doesn't map directly — but if group bookings or multi-court reservations are ever supported (e.g., a coaching session booking multiple courts, or a tournament block-booking several slots at once), the "one parent booking, N child reservation units, each independently cancellable" shape is the one to reach for rather than bolting that onto Facility Booking's single-row model later.

## Two correctness issues worth fixing independent of any of the above

`validate_court_overlap()` in `facility_booking.py` runs a plain `SELECT` to check for conflicting bookings before allowing the insert — there's no row lock, so two near-simultaneous submissions for the same court and time slot can both pass the check before either one commits, and you end up with two confirmed bookings for the same court. Buzz hits this same class of problem with coupon redemption counts and handles it with a row-locked read (`validate_coupon_availability()` selects `for update` before counting existing redemptions) inside the same transaction as the write. The fix here is the same shape: lock the relevant Court row (or a per-slot marker row) with `SELECT ... FOR UPDATE` at the start of `validate_court_overlap()` so the overlap check and the eventual insert are atomic with respect to concurrent requests. This matters more once self-service booking exists and requests can genuinely race — right now, with only staff creating bookings one at a time from the desk, it's a low-probability bug; it becomes a real one the moment there's a public booking page.

Booking Schedule is dead data. It models exactly the "available slot" concept a booking UI needs (per-court, per-day-of-week, start/end/duration, active flag) but nothing reads it — Facility Booking will happily accept a booking at 3am on a court whose Booking Schedule says it's only open 6am–10pm. Either wire it into `validate_times()` (reject a booking whose range isn't covered by an active Booking Schedule row for that court and day-of-week) or, if the intent was always for it to be advisory/UI-only, that's worth confirming — right now it reads as an unfinished feature rather than a deliberate choice.

## Suggested shape, concretely

If you build self-service facility booking, the pieces that map most directly from what's already been read:

A whitelisted, `allow_guest=True` method — call it `get_available_slots(court, date)` — that reads Booking Schedule for that court/day-of-week, subtracts existing non-cancelled Facility Bookings and any Maintenance Schedule rows for that date, and returns the remaining open ranges. This is the "remaining_tickets" equivalent: the thing that makes availability queryable instead of just enforced-after-the-fact.

A whitelisted `create_booking(court, date, start_time, end_time, ...)` that resolves the caller (member login, or guest with the HMAC-token pattern if guest booking is wanted), locks the court row, re-validates the slot is still free, creates the Facility Booking, and — this is the new part — instead of stopping at "Sales Invoice created," calls into frappe_paystack to generate a checkout link and returns it, mirroring how `finalize()` branches in Buzz's `BookingService` between free/offline/pay-online outcomes.

A `Booking Settings` singleton (or new fields on the existing `Sports Complex Setup` singleton) holding something like `allow_cancellation_before_booking_hours` (default, say, 24) and `require_cancellation_approval` (checkbox), read by a `windows.is_window_open`-style helper before allowing a cancellation request to be created or auto-accepted.

If member self-service cancellation is wanted, split Booking Cancellation's current "create it and it's cancelled" behavior into a request/approval pair the way Ticket Cancellation Request does — either a new lightweight doctype for the request, or just adding a `status` field (In Review/Accepted/Rejected) to Booking Cancellation itself and moving the actual status-flip from `validate()`/`on_submit()` into an approval action gated to staff roles (or auto-approved when the time-window check passes and `require_cancellation_approval` is off).

None of this requires touching Court, Sports Facility, Maintenance Schedule, or the existing overlap/maintenance-conflict validation — those are already doing the same job Event Ticket Type's availability math does, just expressed as SQL overlap queries instead of a computed count. The gap is entirely in the layer above them: nothing lets a customer reach that logic without a staff member operating the desk form on their behalf, and nothing connects a confirmed booking to an actual online payment.
